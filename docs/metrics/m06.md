# M6 metrics (branch `m6-hardening`)

M6 T5 measured the voice agent against the real Gemini Live API, tuned the knobs from those
numbers, and measured again. This file holds T5's numbers. The observer adds the milestone's
full report (Lighthouse on both form factors, axe, gate latency, console and CSP checks) at the
end of M6.

## Method (M6 T5, 2026-11-02)

- `npm run e2e:live` at the repo root: the real page, the real server with its real key, model
  `gemini-3.8-live` via `@google/genai` 2.32.0. Three scenarios per run (greeting, task,
  reconnect, `docs/metrics/README.md`). No retries: every failure counts. The numbers come from
  `.metrics/live.json`.

## Knob decisions

### 1. The still-attached retry: 1 s → 400 ms × the attempt (changed)
Gemini refuses an immediate resume with 1008 "already connected" while it still holds the
dropped client. The generic backoff then waited 1 s, so a recovery that needed two attempts took
2.98–3.14 s in the baseline (2.80–3.37 s in M5). Now `STILL_ATTACHED_RETRY_MS = 400` times the
attempt number (400 ms, 800 ms, 1.2 s and so on, never later than the usual backoff), which still
leaves Gemini about 6 s in all to let go.

After the change, two-attempt recoveries took 2.54 s and 2.89 s. Every 400 ms retry resumed: no
recovery needed a third attempt. The worst case fits the budget, but only by 0.11 s. Most of
each attempt is the token fetch plus the socket setup (about 1.0–1.15 s); that, not the delay,
is the lever if the budget gets tighter. Unit test: "retries a still-attached refusal after
400 ms, then 800 ms, and any other close on the usual backoff".

### 2. Knowledge on a resumed reconnect: resent → not resent (M9, changed)
The handoff called the resend deliberate, because a reconnect couldn't trust the resumed
history. Measured:
- The resend costs the whole knowledge text on every drop. That was 386 B here, and up to
  `MAX_TOTAL_BYTES` (4 MB) in principle, stacked as another copy in the session's context.
- With the resend, the resumed session named the seeded code name in 5 of 5 runs. Without it,
  10 of 10.

Resumption carries the knowledge, so the resend is dropped. Two cases still send it: a fresh
session (no handle, or a rejected one), and a resumed session when the store changed while no
session was up. The keyframe is still forced on every reconnect (≤ 855 B), because the page can
change during a drop. Tests: `liveSession.test.js` "knowledge on a reconnect (M9)".

### 3. The stall after navigate: a `next` line in the navigate result (tried, reverted)
The one change aimed at the known stall added this line to a successful navigate's tool
result: "The new page has loaded; it is in `page` when it changed. If the request has remaining
steps, carry on with the next one now."
- With it, the task passed **0 of 3** (runs 24, 25 and 27). Run 27 stalled right after the
  navigate, the very failure the line was meant to fix. In runs 24 and 25 the agent greeted and
  then never acted on the spoken task. No user transcript appeared, in the reconnect scenario
  of the same runs too.
- The baseline code, re-run between them (run 26), passed.

It's not certain the line caused the two unheard runs; they may have been a service-side blip
(13:13–13:17 UTC). But three runs gave no sign of help and one showed the same stall, so it was
reverted rather than spending more runs on it. The system instruction already says to carry
out every step. The task path is now the baseline's code.

### 4. `MAX_SNAPSHOT_NODES` 30 (kept)
Keyframes measure about 100 B per node (777–855 B for the target app's 8 nodes, labels and a
select's options included). So 30 nodes is about 3–3.5 kB, inside the 4 kB budget, and 40 would
not be. These pages never reach the cap, so it is untested at the cap itself.

### 5. `FULL_REFRESH_RATIO` 0.6 (kept)
With 8 nodes, the deltas are 1–2 nodes (a click, a toggle, a confirmation appearing). The final
runs sent 50 keyframes over 30 sessions. That is exactly one at each connect, plus one after each
navigate and one after each reconnect, so the ratio never forced one. Nothing in the data argues for a different ratio. A delta covering 60 % of the page
costs about as much as the keyframe that also resets the model's view. Untested on a larger
page.

### 6. Loop-guard thresholds (kept)
In 14 runs with the `ds:loop-trip` mark (24–37), the guard never tripped, and the five runs
before had no refused action either. The task's longest legitimate repeat is two identical
clicks, under the period-1 limit of 3. So there were no false trips, and there was no true loop
to catch.

## Misses and what is still open

### 1. Task success 8 of 10, exactly the budget (watch)
The two failures in the final runs were not the navigate stall:
- **Run 30:** two clicks, the navigate and the `fill` all succeeded. The model said "I'm
  selecting the Pro plan for your account" and ended its turn with the toggle and Save left.
  It's the same turn-taking stall, now one step later.
- **Run 33:** the voice activity detection split the spoken prompt at "Choose the pro plan." The
  model started acting on the first half, and "notifications and save" arrived as a second user
  turn that interrupted it. The agent then stopped after the navigate. This is partly the test
  prompt's long sentence chain (`say` pauses at each full stop).

On the code path the final runs share with the baseline, the task passed 14 of 16 (runs 19–23,
26, 28–37). That is 88 %, but 16 runs can't tell 80 % from 90 %.

**What I'd try next:**
- an explicit "continue" client turn when a model turn ends with an unfinished multi-step
  request (needs a heuristic, which risks false continues);
- the Live API's `thinkingConfig`, or a lower temperature;
- a prompt with fewer full stops, to measure turn-taking apart from the VAD split.

### 2. Reconnect worst case 2.89 s, 0.11 s under budget
A third attempt (Gemini holding the client longer than about 1.5 s) would cross 3 s. It hasn't
happened in 10 runs. Reusing the token across a reconnect, or fetching the next one ahead of
time, would take about 0.3–0.5 s off every attempt.

### 3. Not measured
- `scroll`'s round trip: the task never scrolls.
- The snapshot cap and refresh ratio on a page large enough to reach them.
