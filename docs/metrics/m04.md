# M4 metrics (branch `m4-closed-loop`, measured 2026-10-28)

First metrics report for this repo, so there is no previous milestone to compare against.
The only baseline is the bundle size the spec records (148.6 kB gzip "today" in
`docs/superpowers/specs/design.md` § Budgets).

Method: `agent-client` production build (`npm run build`), then the Express server on
:3932 (`server/index.js`, log in `.metrics/server.log`). Lighthouse 13 ran headless through
`npx`, mobile and desktop. axe-core 4.10.2 was injected from cdnjs through the Chrome
DevTools MCP into the page and the same-origin iframe, so no repo dependency was added.
`@axe-core/cli` could not run: its ChromeDriver supports Chrome 152 and the installed Chrome
is 156. A Node script made the gate-latency requests with keep-alive and one socket. The
widget was never connected, and no request carried a valid nonce.

How the misses below were closed:
1. `compression` middleware in `server/index.js` and `defer` on both sandbox scripts. Note that
   `compression` skips HEAD requests by design, so `curl -sI` never shows `content-encoding`;
   check with a GET (`curl -s -o /dev/null -D - -H 'Accept-Encoding: gzip' …`).
2. `title="Target app"` on the iframe, `<main>` on all three pages, the knowledge button's
   `aria-label` and no `opacity` on its empty state. Adding `<main>` to both the sandbox and the
   framed page raised a new `landmark-unique` (axe treats the frame as one tree), fixed by
   `aria-label="Target app sandbox"` on the sandbox's `<main>`.
3. Viewport and description metas on all three pages.
4. A `data:` favicon on both target-app pages; the search input now has an `id`, a `name` and a
   visually hidden `<label>`.
5. Unused JS (genai loaded before Connect) is unchanged; it no longer threatens a budget.

The ranked findings below are the observer's original analysis, kept as written.

Rate-limiter handling: in `server/index.js` the order is `isSameOrigin` → `isRateLimited` →
`isValidNonce`. Cross-origin 403s return before the limiter counts them, so all 50 ran in
one go. The no-nonce run does count toward the limit of 30/min per IP. To keep it under the
limit, it was split into 3 warm-up + 25 measured requests from `127.0.0.1` and the same from
`::1`. Ten more requests from `127.0.0.1` then returned 2 × 403 and 8 × 429, as expected.

## Misses, ranked by impact

### 1. Must fix: mobile Perf 75 and LCP 4.26 s on `/` (the server does not compress)
- **Cause:** Express serves `agent-client.js` uncompressed. Lighthouse shows a transfer
  size of 622,222 bytes, against 148 kB gzipped. The script is also a classic
  render-blocking `<script>` in `sandbox/index.html`. Lighthouse's `render-blocking-insight`
  puts the cost at 3,350 ms for `agent-client.js` and 300 ms for `bridge.js`. The LCP element
  is the agent card (`div.agent-app`), which renders only after that script runs.
- **Evidence:** in `.metrics/lh-root-mobile.json`, `network-requests` shows a transfer size
  of 622,222 bytes for `agent-client.js`, and `render-blocking-insight` the numbers above.
  `server/index.js` has no compression middleware.
- **Fix:** add the `compression` middleware (`app.use(compression())` before the static
  routes) in `server/index.js`. An experiment put a throwaway gzip proxy in front of the same
  server (not committed). Mobile `/` then scored Perf **98** with LCP **1.86 s**, so this one
  change clears the budget. Also check whether Render compresses in front of the app; the
  middleware is correct either way.
- **Worth doing:** add `defer` to the two `<script>` tags in `sandbox/index.html`. Lighthouse
  still reports 960 ms of render-blocking savings after compression. Check that `bridge.js`
  still runs before `agent-client.js`; `defer` keeps their order.

### 2. Must fix: A11y 80 on `/`
- `frame-title` (serious): `<iframe id="target-app-frame">` in `sandbox/index.html` has no
  title. **Fix:** `title="Target app"`.
- `color-contrast` (serious, from Lighthouse's axe): `.agent-app__knowledge-btn--empty` has
  `opacity: 0.5` (`agent-client/src/main.jsx:39`), which gives #7e7e7e on #f7f7f7 = 3.78:1
  against a required 4.5:1. The axe 4.10 run in the browser marked this node "incomplete"
  because of the 📄 emoji, so it is real but was not auto-confirmed there. **Fix:** remove the
  opacity and show the empty state another way, such as the existing red inset ring or muted
  text at ≥ 4.5:1.
- `landmark-one-main` and `region`: neither the sandbox page nor the target-app pages have a
  `<main>`. **Fix:** wrap the iframe in `<main>` in `sandbox/index.html`. Wrap the content
  after `<nav>` in `<main>` in `target-app/index.html` and `settings.html`.
- Not an axe violation but related: the knowledge button's accessible name is "📄 0". Give it
  `aria-label="Knowledge files (0)"` (`agent-client/src/AgentApp.jsx:56`).

### 3. Must fix: SEO 90 on both routes (`meta-description`)
- **Cause:** there is no `<meta name="description">` in `sandbox/index.html` or the
  target-app pages. Lighthouse's `viewport-insight` also scores 0.5 because there is no
  `<meta name="viewport">`.
- **Fix:** add both meta tags to the three HTML files. The budget says SEO 100 on `/`. For a
  demo harness SEO has little real meaning, so the user may prefer to accept SEO on the
  target-app mock pages rather than fix it. If so, write the reason here.

### 4. Must fix: Best Practices 96 and a console error on `/target-app/index.html` (favicon 404)
- **Cause:** when loaded on its own, the page requests `/favicon.ico` and gets a 404, which
  logs a console error (`errors-in-console`). Inside the sandbox, `<link rel="icon"
  href="data:,">` on the parent avoids this.
- **Fix:** add `<link rel="icon" href="data:," />` to both target-app pages, the same as
  `sandbox/index.html`.

### 5. Worth doing: unused JS (Lighthouse estimates 477 KiB of the bundle unused on load)
- **Cause:** by minified bytes from a scratch sourcemap build, `@google/genai` is 343 kB of
  622 kB and `react-dom` is 207 kB. The app's own `src/` is 15 kB. genai is needed only on
  Connect, but the IIFE library build cannot code-split.
- **Fix (later, not needed for the budget):** load the Live SDK lazily at Connect, for
  example from a second script the widget injects on click, or build an ES module with a
  dynamic `import()`. Compression fixes LCP without this. This is the lever to use if the
  bundle grows toward 165 kB in M7.

## Alarming but within budget
- **The server has no request logging.** `.metrics/server.log` contains only the "listening"
  line. The run served about 50 page loads and 140 token-gate requests, and none were logged.
  "0 × 5xx" therefore means only that no `console.error` mint failure fired. The spec's pino
  request log (request id, route, status, duration) does not exist yet. Until it does,
  5xx and slow-request checks are blind.
- DevTools issue "A form field element should have an id or name attribute": the search
  `<input>` in `target-app/index.html`. It is harmless, but it will show up in an e2e
  console listener that counts issues.

## Manual checks for the user (a few minutes, needs the real key)
1. **Connect time and greeting:** run `cd server && npm start`, then open `http://localhost:3000/`
   in Chrome with DevTools Network open. Click Connect and allow the mic. Expect the status
   to go Connecting → connected in ≤ 2.5 s and the greeting audio to start ≤ 2 s after that.
   Expect exactly one `/api/live-token` request with status 200.
2. **Reconnect (A2/B2, idempotent connect):** while connected, set Network throttling to
   "Offline" for about 3 s, then back to "No throttling". Expect "reconnecting" and then
   connected within about 3 s. In the console, run
   `performance.getEntriesByType('resource').filter(r=>r.name.includes('live-token')).length`;
   it should be 2. Only one voice should be audible, never two.
3. **Retry and failed state:** stop the server while connected. Expect a "failed" status
   with a `role="alert"` reason and a Retry button. Restart the server and click Retry. The
   token request will 403 because the server restarted and the nonce is gone. Expect an
   honest failure message telling you to reload, not a hang.
4. **Tool round-trip:** ask "go to settings and enable notifications". Expect the iframe to
   navigate and the checkbox to toggle, with no `postMessage` errors in the console. That
   checks the MessageChannel from T2.
5. **Render compression:** after deploy, run `curl -sI -H 'Accept-Encoding: gzip'
   https://<render-host>/agent-client/agent-client.js | grep -i content-encoding`. If there
   is no output, compression is missing in production too.
