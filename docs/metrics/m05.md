Compared with M4's "after the fix wave" column (`docs/metrics/m04.md`), the state that was merged.

Method: `npm run check` at the root, which runs Prettier, ESLint, `tsc`, both vitest suites and
the `agent-client` production build. The Express server ran on :3993 (`server/index.js`) with a
dummy `GEMINI_API_KEY` and dotenv pointed at `/dev/null`. Its pino log went to
`.metrics/server.log`. Lighthouse 13 ran headless through `npx`, mobile and desktop, with JSON in
`.metrics/lh-m05-*.json`. A Playwright script (Chromium, from the repo's
`@playwright/test` and `@axe-core/playwright`) loaded each route. It recorded console
errors and warnings, page errors, failed requests, HTTP ≥ 400 responses, DevTools issues and a
`securitypolicyviolation` listener in every frame, then ran axe. A positive control (an inline
`<script>` injected into the page and into the iframe) confirmed that CSP violations are
enforced in both frames and show up as console errors. A Node script measured gate latency with
keep-alive and one socket per address family: 50 warm requests per path, split between
127.0.0.1 and ::1 for the rate-limited paths, with a 62 s pause between batches so the 30/min
limit never mixed in. The live numbers come from `.metrics/live.json` (11 runs, M5 T5). The
live suite was not re-run.

## Misses

### 1. Scripted task success 8 of 11 (73 %), under 80 % (Must fix, planned for M6 T5)
- **Cause:** all three failures (runs at 05:39, 05:44 and 05:49 UTC) stall the same way. The
  agent narrates the navigate to Settings and the navigate succeeds (bridge round trip ≤ 25 ms),
  then the model ends its turn without the next step, so `expect(locator).toBeVisible()` on the
  save confirmation times out. This is model turn-taking, not the bridge. M5 T5's held-snapshot
  fix (the keyframe now travels inside the tool response) took the task from 0 of 4 to 8 of 11.
- **Resolution:** M6 T5 tunes the system instruction and tool-response handling against this
  baseline (plan commit `831b5ec`).

### 2. Reconnect recovery worst case 3.37 s, over 3 s (Must fix, planned for M6 T5)
- **Cause:** Gemini refuses an immediate resume with close code 1008 "session is already
  connected to an existing client" while it still holds the dropped client. The backoff's next
  attempt (`RECONNECT_DELAYS[1]` = 1000 ms, `agent-client/src/liveSession.js:52`) then resumes.
  One attempt takes 1.01–1.35 s and two take 2.80–3.37 s. 4 of 11 recoveries needed two
  attempts and 1 of them crossed 3 s.
- **Resolution:** M6 T5 uses a shorter delay before retrying that specific refusal
  (`SESSION_STILL_ATTACHED`, `liveSession.js:71`), for example 300–500 ms instead of the generic 1 s.

### 3. Not measured: fill/scroll round trip and keyframe payload
The live task never calls `fill` or `scroll`, and no mark records the keyframe size. The
deterministic `bridge.spec.js` exercises both actions but does not time them. **Worth doing:**
add a `fill` step to the live task prompt and a `ds:keyframe` mark with `detail.bytes` in M6 T5.

## Findings that are not budget misses

### 1. A failed Gemini mint is answered as a client 400, logged at warn (Worth doing, high priority)
- **Evidence:** a Connect click with the dummy key sent one real mint request. Google answered
  `API_KEY_INVALID`, which the SDK throws as an `ApiError` with `status: 400`. `handleError`
  (`server/app.js:293–305`) trusts any `err.status` in 400–499 as the caller's fault. The
  log shows `{"level":40, … "err":{"type":"ApiError", … "status":400},"msg":"request rejected"}`
  and the browser got `400 bad_request` after 515 ms. In `liveSession.js:341–342` a 400 is
  non-retryable and shows "Reload the page to reconnect", which a reload cannot fix. An
  upstream 429 (quota) is passed through the same way as a 429.
- **Why it matters:** a broken or revoked production key never appears as a 5xx or an
  `error`-level line, so the "0 × 5xx" check and any Render alert on errors miss it. The user
  is also told to do something that cannot work.
- **Fix:** catch the mint rejection in the `/api/live-token` handler (`app.js:255`) and answer
  `502 { code: 'mint_failed' }`, logged at `error` with the request id. Or have `handleError`
  honor `err.status` only for errors that set `expose: true` (http-errors, which Express's own
  4xx use), never for upstream SDK errors. Add a supertest case with a `mintToken` that rejects
  with `{ status: 400 }`.

### 2. `ScriptProcessorNode` deprecation warning on Connect (Worth doing, M7)
Chromium logs "The ScriptProcessorNode is deprecated. Use AudioWorkletNode instead." when the mic
starts (`audioIO.js`). It is a warning, not an error, so the e2e fixture allows it. Moving to an
`AudioWorklet` needs `worklet-src`/`script-src` coverage in the CSP (a module from `'self'` is
already allowed).

### 3. Unused JS on `/` unchanged (Worth doing, not urgent)
Lighthouse estimates 111 KiB of the 146 KiB transfer unused on load, the same as M4. Most of
it is `@google/genai`, which is only needed after Connect. It is the lever to pull if M7's toast,
orb and web-vitals push the bundle toward 165 kB.

## Alarming but within budget
- **`style-src 'unsafe-inline'`** is a deliberate gap in the CSP (the shadow-root `<style>` and
  Radix's injected styles, documented in `server/app.js`). Script injection is still blocked.
  Record it in `docs/code-review-notes.md` H1 so the decision isn't lost.
- Lighthouse 13 probes `/llms.txt`, `/robots.txt`, `/.well-known/ard.json` and

- The unknown-nonce path has the widest latency spread (max 4.0 ms against p95 0.78 ms). That is
  still about 60× under budget and is probably the one-off `ExpiringMap` sweep. No action needed.

## After the fix wave (2026-10-29)

- **Finding 1 is fixed** (`server/app.js`): the route catches the mint rejection. An upstream
  400/401/403 is `500 not_configured` and any other failure is `502 upstream_error`, both logged
  at `error` with the request id; `handleError` keeps a 4xx only for an `expose`d client error.
  Verified against the real Google endpoint: the server ran on :3994 with
  `GEMINI_API_KEY=invalid-key DOTENV_CONFIG_PATH=/dev/null DOTENV_CONFIG_QUIET=true`, and a
  Connect click from `/` in Chromium got **500 `not_configured`**. The log has one
  `"level":50 … "msg":"live token mint failed"` line with the `reqId` and the SDK's
  `API_KEY_INVALID` detail, which stays server-side. The card shows "Connection lost", the alert
  "The server isn't configured to connect. Contact the site owner, then reload this page." and
  a "Reload page" button. The only console error is the browser's own line for the 500.
  Supertest covers 400/401/403 → 500, 503/429/no-status → 502, and a plain thrown error → 500
  `internal`.
- **Bundle:** `agent-client.js` 624.5 kB raw, **150.6 kB gzip** (+0.1 kB for the snapshot
  `value` and the mark clearing), still under 165 kB.
- **Tests:** `agent-client` 110 in 10 files, `server` 44 in 2 files, `npm run e2e` 13 of 13 in 3
  consecutive runs. After the second, smaller wave (hidden and secret fields, more field
  names, the HTML 429): 118 and 46, e2e 13 of 13.
- **Live e2e, 3 runs after the fix wave** (runs 12–14 in `.metrics/live.json`): greeting 3 of 3,
  reconnect 3 of 3 (one attempt each, 0.91–1.41 s), task **2 of 3**. The failure is the same
  stall as miss 1: two clicks and the navigate succeed, then the model ends its turn on "I am
  navigating to the settings page". The task never calls `fill`, so the snapshot `value` field
  changes only what the model reads (the search field now carries `value: ""`). Across the 14
  runs the task stands at 10 of 14 (71 %); miss 1 stays with M6 T5.
- No CSP violations or console errors on load of `/`; the HTML 404 renders with its heading and
  "Back to the demo" link; the knowledge dialog's textarea now ends at the dialog's inner edge
  (`box-sizing: border-box`).

## Manual checks for the user (a few minutes, needs the real key)
1. **Strict CSP with a real session:** run `npm run dev`, open `http://localhost:3000/` with
   DevTools Console open, click Connect, talk for 20 s, and ask "go to settings and turn on
   notifications". Expect zero lines containing "Content Security Policy" in the top frame and in
   the `target-app` frame (pick it in the console's context dropdown). The Live socket to
   `wss://generativelanguage.googleapis.com` must open; a `connect-src` violation would show here
   first.
2. **Log hygiene with a real mint:** in the same run, check the server's stdout. Expect one
   `live token minted` line with a `reqId` and no `token`, `nonce=` or key text on any line.
3. **Mint failure path (finding 1, fixed):** stop the server, start it with
   `GEMINI_API_KEY=invalid npm start`, reload and click Connect. Expect a `500` with
   `not_configured`, an `error`-level `live token mint failed` log line, and the alert "The
   server isn't configured to connect. Contact the site owner, then reload this page."
