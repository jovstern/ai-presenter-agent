## Method (2026-11-07)

- **Machine load:** very high throughout (10 cores). The load average was 16–22 at the start,
  peaked at **170** during the first Lighthouse round, and was 20–120 for the rest. So:
  - Lighthouse ran 3 times per route and form factor, `/` mobile 7 times and Orders mobile
    5 times, and the table gives medians.
  - The load at each round's start is in `.metrics/lh-m09obs-load.txt`.
  - Timing numbers (TBT, latency) are noisier than in M7. Scores and CLS are not affected,
    except where noted below.
- **Server:**
  - Built with `npm run build` in `agent-client/`.
  - Served by `node index.js` from `server/` on **:3191**, with `GEMINI_API_KEY` empty and
    dotenv pointed at `/dev/null`, so the token route answers `not_configured` without calling
    Google.
  - The brief's :3100 was already taken by another server from this repo (PID 26310, started
    14:41:14 by someone else). It was left running and untouched.
  - The pino log is `.metrics/server-m09-observer.log`. The server was stopped afterwards.
- **Lighthouse 13.6**, headless, mobile and desktop, on `/` and the three target-app pages
  (`.metrics/lh-m09obs-<route>-<form>-<n>.json`). `/sandbox/` was not re-run: it is the same
  page as `/`.
- **Playwright probe** (the repo's `@playwright/test`, `@axe-core/playwright` and
  `e2e/fakeLive.js`, with `baseURL` set):
  - 16 states, each in light and dark: the three target pages; `/` idle, then hovered; `/`
    with Talk focused by keyboard; the knowledge dialog open (after its fade); failed against
    the real `not_configured` route, with its toast settled; and Live with a transcript, then
    reconnecting.
  - Each state records console errors and warnings, page errors, failed requests, HTTP ≥ 400
    responses, `securitypolicyviolation` events in every frame, every SDK-chunk request, and
    a `layout-shift` observer. Then axe runs.
  - Two extra runs: the orb's reconnect pulse with the setup held back, so the card stays in
    Reconnecting, in normal and reduced motion; and Orders with `orders.js` delayed by 0, 300
    and 1000 ms at 412 px.
- **`npm run e2e`**, once.
- **Gate latency:**
  - A Node `fetch` loop, 5 warm-up requests, then 10–50 timed requests per path.
  - The token limiter (30 a minute per IP) caps the same-origin paths at 10–20 samples.
  - The first `/api/client-log` series ran during Lighthouse (p95 16 ms), so it was repeated.
- **Live e2e:** not run, as briefed. Its numbers below come from runs 65–69 in
  `.metrics/live.json` and `README.md` § M9 T2 and § M9 T6.

## Misses

### 1. Orders page CLS 0.679 on mobile, Perf 77 (Must fix, CLS ≤ 0.05 and Perf ≥ 95)

- **Evidence:**
  - Lighthouse mobile on `/target-app/orders.html` measured CLS **0.679** (Perf 77) in runs
    1, 4 and 5, and 0 (Perf 100) in runs 2 and 3. `layout-shifts` names a single shift:
    `body.wide > main > section` ("New order", `aria-labelledby="new-order-heading"`), which
    ends at top 2938 px, height 1031 px.
  - The probe reproduces it deterministically at 412 px:
    - `orders.js` delayed 300 ms or 1000 ms: one shift of 0.679;
    - not delayed, on this machine: 0.
- **Cause:**
  - `target-app/orders.html:45` ships an empty `<tbody id="orders-body"></tbody>`.
  - The 60 rows are built by `target-app/orders.js` (`orderRow`, from line 35), loaded with
    `<script defer>` (`orders.html:160`).
  - A deferred script runs after parsing ends, and Chrome may paint before then. When it does
    (a busy CPU here; on a real network, any delay in fetching `orders.js`), the first frame
    has an empty table, with the New order form just under the toolbar, in view.
  - The rows then push the form down about 2,900 px. Nobody provoked the shift, so it counts
    in full.
- **Who sees it:**
  - Anyone loading Orders on a slow link, including inside the sandbox iframe when the agent
    navigates there. Chrome's field CLS counts shifts in iframes towards the embedding page.
    `clientLog.js` reports the top frame's CLS only, so the server's `client vital` lines
    would not show it.
  - Desktop measured 0 in its three runs, but the mechanism does not depend on width. It was
    not reproduced at desktop width with a delayed script.
- **Fix (in order):**
  1. Put the 60 rows in `orders.html` as static markup. The data is fixed by design: "the
     same data on every load, so a test can name an order". `orders.js` then only wires the
     checkboxes, Ship, the count and the form, so nothing that arrives late changes the
     layout. The page is a test fixture, so the extra markup (~60 lines × ~300 B, which
     gzips well) costs nothing that matters.
  2. If generated rows must stay, reserve the space. For example, hide `main` until the rows
     exist (`visibility: hidden` until `orders.js` sets a class), or give the table's
     container a fixed height and let it scroll. A `min-height` sized to 60 rows is fragile at
     phone width, because the rows wrap.
  3. Add the regression test. In `e2e/a11y.spec.js` or `bridge.spec.js`, delay
     `**/target-app/orders.js` by 300 ms with `page.route`, load the page, and assert that a
     `layout-shift` observer sums to < 0.05. The probe that found it is the recipe
     (`page.route` with a `setTimeout`, then `PerformanceObserver({ type: 'layout-shift',
     buffered: true })`).

  The bridge's snapshot numbers in `README.md` § M9 T6 do not change: they are taken after the
  page settles.

## Worth doing (not budget misses)

1. **The live connect budget now includes the SDK chunk, and it was only measured on
   localhost.**
   - Live run 69's connects reached **2.23 s and 2.10 s** against the 2.5 s budget. Runs 65–68
     (also after T1) peaked at 1.62 s.
   - On localhost the 74.66 kB chunk takes no time. On Render over a phone network it is
     ~0.3–0.6 s, in parallel with the token request.
   - The hover and focus preload hides it for a mouse or keyboard user. A touch user's first
     tap starts the preload and the connect together.
   - Measure connect → `open` on the deployed site with DevTools' "Fast 4G" throttle before
     calling the budget safe (manual check 1).
2. **The SDK chunk has 5.34 kB of headroom.** A `@google/genai` minor version could use it
   up. `e2e/sdk.spec.js` already fails the build past 80 kB, so this is a watch item, not a
   fix.
3. **`/` mobile TBT median 44 ms, against 13 ms in M7.**
   - The bundle is 40 % smaller, the long tasks are still `agent-client.js` evaluation and
     first render, and the two runs at lower load measured 3–4 ms.
   - This is the machine's load (16–170), not the code. Re-check on a quiet machine before
     reading a trend into it.
4. **The 500 for `not_configured` is logged at info.**
   - pino-http leaves a 5xx response at info, and the app logs no error line for this path (by
     design: it is a configuration state, not a fault).
   - In production `NODE_ENV=production` makes a missing key fatal at start-up, so this
     can't happen there. Locally it only makes a grep for 5xx noisier.
   - No change is needed. It is noted so a later reader doesn't take the 27 × 500 as errors.
