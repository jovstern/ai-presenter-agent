## Method (2026-11-06)

- `npm run check` and `npm run e2e` at the root, the e2e three times.
- The production build (`npm run build` in `agent-client/`) served by `node index.js` from
  `server/` on :3991 with a dummy `GEMINI_API_KEY` and dotenv pointed at `/dev/null`. Its pino
  log is `.metrics/server-m07-observer.log`.
- Lighthouse 13.6, headless, mobile and desktop, on `/`, `/sandbox/` and both target-app pages
  (`.metrics/lh-m07obs-*.json`). `/` mobile ran five times (`-2` to `-4` are the repeats).
- A Playwright script (the repo's `@playwright/test` and `@axe-core/playwright`, plus the
  fake-Gemini harness in `e2e/fakeLive.js`). It loaded 13 states and recorded console errors and
  warnings, page errors, failed requests, HTTP ≥ 400 responses and `securitypolicyviolation`
  in every frame, then ran axe on each one. The states: the two target-app pages, `/sandbox/`,
  and `/` idle, with the knowledge dialog open, failed with its toast, and Live with a transcript
  and a navigate tool call, each of the `/` states in light and dark.
- **Runtime cost while Live**, on the same page through the fake-Live harness:
  - main-thread time from CDP `Performance.getMetrics` (task, script and style-recalc time per
    second) over 10 s windows;
  - long tasks from a `PerformanceObserver`;
  - React commits from a counting `__REACT_DEVTOOLS_GLOBAL_HOOK__`, installed before the bundle
    (production `react-dom` reports each commit to it);
  - the JS heap after a forced GC at 0, 10, 20 and 30 s of streamed agent speech.

  The control is the same Live session under `prefers-reduced-motion: reduce`, which stops the
  orb's loop. The windows ran once unthrottled (desktop) and once at 4× CPU throttling and
  390 px width.
- **Layout shift after load**: a `layout-shift` observer while a Live session's transcript grows
  over six turns, at 1280 × 800 and 390 × 844, grouped into CLS session windows (1 s gap, 5 s
  cap).
- Bundle breakdown: a sourcemapped copy of this build and of `master` (M6's final state,
  `git archive` + `npm ci`), attributed per package with a VLQ decoder. A variant build without
  the React Compiler gives the compiler's own cost.
- The live suite was **not** run (the brief). Its numbers are `.metrics/live.json`.

## Misses

### 1. CLS from the card's transcript at phone width, 0.15 (Must fix, CLS ≤ 0.05)

- **Evidence:**
  - Setup: a Live session through the fake-Live harness, the transcript growing over six turns,
    with a `layout-shift` observer on the page. None of the shifts has `hadRecentInput`.
  - At 390 × 844 the session windows are 0.011, 0.010, 0.110, 0.122, **0.151**, 0.125, 0.026,
    0.126 and 0.124. At 1280 × 800 the worst is 0.032.
  - The large shifts' source rects are the card itself: y 541 → 517, height 303 → 327. The top
    edge moves 24 px, one line, each time a transcript line wraps or a turn is added. The card
    grows (147 → 203 → 259 → 283 → 307 px) and shrinks back (327 → 303) when the oldest of the
    three visible turns drops out. Smaller shifts (0.002–0.01) are the 18 px text lines moving up.
  - **A single line wrap is 0.087–0.124 at 390 px**, so even unhurried speech, where wraps fall
    in separate windows, breaks the budget on every wrap.
  - Lighthouse doesn't see this. Load CLS is 0 on every route, because nothing shifts until a
    session is Live.
- **Cause:** the card is `position: fixed; bottom` (`:host`, `agent-client/src/styles.css:26`).
  The transcript sizes to its content up to `max-height: var(--transcript-max-height)` (200 px,
  `styles.css:331-339`). It uses `flex-direction: column-reverse`, and `Transcript.jsx` keeps the
  last 3 entries (`VISIBLE_ENTRIES`). So every wrapped line moves the card's top edge and
  everything in it. Each turn that pushes the oldest out of the slice moves every line. CLS counts
  shifts with no recent input for the page's whole life, and speech isn't input. A host page that
  embeds the widget would see its real-user CLS go over 0.1 ("needs improvement") on phones.
- **Fix (in the order to try):**
  1. Reserve the transcript box while Live. Use `height: var(--transcript-max-height)` instead of
     `max-height` once the transcript has entries, or as soon as the status is `open`. The card
     then resizes at most once per session: when it opens, within 500 ms of the Talk click, which
     CLS excludes as recent input.
  2. Inside the fixed box, flow the list top-down and keep the newest line in view with
     `scrollTop = scrollHeight` after each fragment. CLS subtracts scroll offset changes, so
     scrolling moves nothing. Don't use `column-reverse` with slicing, which moves the existing
     lines on every new line. If the 3-entry slice stays, removing the top entry is a shift;
     keeping more entries and letting them scroll away avoids it.
  3. Add the layout-shift check to `e2e/widget.spec.js` at 390 px: grow the transcript over a few
     turns and assert that the worst session window is < 0.05. The observer script that measured
     this is the recipe (`PerformanceObserver({ type: 'layout-shift' })`, `hadRecentInput` false).

### 2. Flaky axe check of the failed toast (Must fix, a flaky gate)

- **Evidence:** the first of three `npm run e2e` runs failed `e2e/a11y.spec.js:69` "dark scheme
  › the sandbox page with the card failed and its toast". axe reported `color-contrast` on
  `.toast__action` ("Reload page"): 4.47:1, `#cacacb` on `#565658`. The test then passed in two
  full runs and 20 `--repeat-each` runs, so it failed 1 time in 26.
- **Cause:** the toast fades in (`animation: toast-in var(--duration-base)`, 200 ms, from
  `opacity: 0`; `styles.css:562`, keyframes at `:602`). The test runs axe as soon as
  `toasts.toHaveCount(1)` passes (`a11y.spec.js:75-80`). If axe samples during the fade, it sees
  the toast's colours blended with the page behind. The settled toast passes: the observer's own
  run, 600 ms after the toast appeared, had 0 violations in both schemes. This is a test race,
  not a contrast bug.
- **Fix:** before `analyze`, wait for the toast's animations to finish. For example:

  ```js
  await toasts.first().evaluate((el) =>
    Promise.all(el.getAnimations({ subtree: true }).map((a) => a.finished)),
  );
  ```

  `page.emulateMedia({ reducedMotion: 'reduce' })` also works if `styles.css` drops the
  animation under reduced motion. Do the same anywhere else axe runs on something that animates
  in, like the dialog's overlay.

## Worth doing (not budget misses)

1. **Bundle margin 4.59 kB before M8.** M8's `web-vitals` and the beacon leave about 1.5 kB.
   Options, cheapest first:
   - Import only `onLCP`, `onCLS` and `onINP` from `web-vitals` (it tree-shakes per metric).
   - Drop the Toast and build the one failure notice on the existing `role="alert"` plus a
     small hand-rolled region (saves ~7 kB). Only if the toast's swipe and announce behaviour
     isn't needed.
   - M6's options C (direct WebSocket, ~60 kB saved) and D (load the SDK on Connect) still
     stand.
2. **The orb's per-frame cost: about 60 ms/s at 4× CPU.** The loop writes `--level` and
   `--mic-level` on every frame (`VolumeOrb.jsx:66-72`). That triggers a style recalc of the
   pseudo-elements and a repaint 58 times a second while Live, even when the formatted value
   hasn't changed. Measured: 0 layouts, 0 commits and no long tasks. That is about 6 % of a
   mid-range phone's main thread, or about 2 % on a desktop. Two cheap trims:
   - Skip `setProperty` when the `toFixed` string equals the last one written. It already sits
     at `0.000` between the agent's turns, and the mic's decay passes through many identical
     2-digit values.
   - Round to 2 decimals.

   Halving the rate (every other frame) would also halve it with no visible loss at these
   easing speeds.
3. **The `/` mobile long task count went from 1 to 2** (53–91 ms each, the bundle's evaluation
   and then the first render). TBT stays at 13 ms median. One run of five reached 53 ms TBT
   (91 + 73 ms tasks), well under 150 ms. The extra evaluation work is the bigger bundle plus the
   inlined stylesheet. Nothing to do now. Watch it as the bundle grows.
4. **e2e wall time 13.8–21 s** (M6: 8.3 s), from 32 tests instead of 21 and the widget demo's
   deliberate 700 ms pauses. It's fine. The 21 s run was the third back-to-back run on a warm
   machine, so the spread is load, not a test.
